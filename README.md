# 投研小工具（飞书 + 大模型）

把投资团队日常的重复劳动变成**一条命令 / 一句话**就能完成的小工具。

对应投研同事每天都在做的三件事：

| 动作 | 平时怎么做 | 现在 | 输出 |
|---|---|---|---|
| **找资料** | 翻一堆报道，手工往表里填公司和轮次 | `industry` | 结构化融资事件表（7 字段，可直接进 Excel） |
| **看材料** | 读几十页文档，自己划重点 | `digest` | 要点 / 数据点 / 风险 / **待确认问题** |
| **开会** | 会后手写纪要，容易漏待办 | `minutes` | 议题 / 决议 / **待办（含负责人和时间）** / 风险 |

结果可以直接推送到**飞书群**（卡片消息），投研同事不用装任何东西。

> 数据声明：本项目**只处理公开信息**，不涉及任何机构的内部数据。
> 仓库里 `samples/` 与 `eval/` 中的公司名、人物、数字**全部是虚构占位**，仅用于跑通流程与评测。

---

## 怎么跑

```powershell
# 不需要 API key，先用规则模式确认流程能跑通
python main.py industry --input samples/industry_news.txt --offline
python main.py digest   --input samples/company_doc.txt --offline
python main.py minutes  --input samples/meeting_transcript.txt --offline

# 换成真模型（任何 OpenAI 兼容接口都行）
$env:LLM_API_KEY="sk-xxxx"
$env:LLM_BASE_URL="https://api.deepseek.com/v1"
$env:LLM_MODEL="deepseek-chat"
python main.py industry --input samples/industry_news.txt

# 推到飞书群（配置见 docs/feishu_setup.md）
$env:FEISHU_WEBHOOK="https://open.feishu.cn/open-apis/bot/v2/hook/xxxx"
python main.py minutes --input samples/meeting_transcript.txt --feishu
```

只用标准库，**没有任何第三方依赖**——`git clone` 下来就能跑。

## 实测效果（规则模式，8 条样本 / 48 个字段）

```powershell
python eval/run_eval.py          # 规则模式（不需要 key）
python eval/run_eval.py --llm    # 模型模式（需要 key）
```

实际跑出来的结果：

```
company     8/ 8  100.0%
industry    8/ 8  100.0%
round       8/ 8  100.0%
amount      8/ 8  100.0%
investors   4/ 8   50.0%
date        8/ 8  100.0%
整体       44/48   91.7%
```

**我特意把弱项写在最前面**：`investors` 只有 50%。四条错例全部是同一类问题——
机构名的边界切不对：

| 输入写法 | 期望 | 实际抽到 |
|---|---|---|
| 由示例天使基金投资 | 示例天使基金 | 示例天使基金**投资** |
| 由示例创投领投 | 示例创投 | 示例创投**领投** |
| 投资方包括示例国际、示例资本 | 示例国际、示例资本 | **包括**示例国际、示例资本 |
| 由示例医疗基金领投 | 示例医疗基金 | 示例医疗基金**领投** |

**结论很清楚**：字段靠"位置"能切准，靠"语义"就切不准——这正是该交给模型、
而不是继续堆正则的地方。这也是我留着 `--llm` 那条路的理由。

## 健壮性：8 个边界用例，修掉 3 个会直接崩的问题

| 用例 | 修复前 | 修复后 |
|---|---|---|
| **GBK 编码**的文本文件（Windows 记事本存成"ANSI"） | `UnicodeDecodeError` 崩溃 | 依次尝试 `utf-8-sig → utf-8 → gb18030`，正常抽出 |
| **带 BOM 的 UTF-8** 文件 | Windows GBK 控制台下 `print` 抛 `UnicodeEncodeError` | 强制 stdout/stderr 走 UTF-8，不可编码字符降级替换 |
| **输入文件不存在** | 裸 traceback | 中文提示 + 退出码 2 |
| **没配 `FEISHU_WEBHOOK` 却加了 `--feishu`** | 裸 traceback | 提示指向 `docs/feishu_setup.md` + 退出码 3，本地结果照常写出 |
| 没有 API key 且没加 `--offline` | 静默降级 | 打一行明确提示，输出里也标 `offline` |
| 空文件 / 无匹配内容 / `--text` 只有空格 | — | 正常输出「共 0 条」，不崩 |

**为什么单列这一节**：投研同事会直接拿手边的文件来跑——**崩一次，他们就不会再用第二次**。
工具的门槛不在功能多少，在"拿到手能不能一次跑通"。

## 已知失败案例（真实跑出来的，不是设想）

**任务三（会议纪要），规则模式下：**

| 现象 | 原因 | 影响 |
|---|---|---|
| 会议标题"本周项目例会"被当成待办 | 命中关键词"本周" | 待办列表里混进一条噪音 |
| 负责人抽成"**芳下周**" | 正则把人名边界和第几个字切错 | 负责人字段不可直接采信 |
| 同一条"代持需在交割前清理"同时进了**决议 / 待办 / 风险** | 启发式规则之间没有互斥 | 需要人工去重 |

**这些不是 bug 列表，是"规则模式的上限"的证据**——所以它只用来在没有 key 时
验证流程跑通，真正的抽取交给模型。

## 工程上几个刻意的取舍

1. **金额一律保留原文，不做单位换算。**
   "数千万""近亿元""未披露"这些写法，机器换算是**给自己埋错**。
   宁可把原文交给投资人判断，也不要在数据里放一个看起来精确、实际算错的数。
2. **把模型输出当作不可信输入。**
   `llm.py` 会剥掉 Markdown 围栏、按括号深度找第一个完整 JSON、解析失败追加修复提示重试。
   模型返回不合法 JSON 是常态，不是异常。
3. **两套模式，且明确标注。**
   输出和 README 里都写着当前是 `offline` 还是 `llm`。**让人一眼知道这份结果的成色**，
   比悄悄降级后装作没问题更重要。
4. **`--offline` 的存在是为了"能验证"，不是为了"能用"。**

## 局限与下一步

- **只做了单向推送**：本地 → 飞书群。JD 里说的"**一句话就能完成**"需要**接收**群消息，
  那要用飞书**自建应用 + 事件订阅**，不是自定义机器人。这是路线图第一步。
- **结果还没有写进飞书多维表格**（现在是本地 CSV + 群卡片）。
- **评测集只有 8 条**，且句子规整；真实报道的长句、多主体、多轮次还没覆盖。
- 文档摘要（`digest`）目前是"抽句子"，模型模式下才是真正的分析。
